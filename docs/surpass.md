# 兼容 + 超越：Nodio 相对官方 aardio 的超越清单

> 目标不是「和 aardio 一样」，而是**行为兼容**之后**做得比官方更好**。
> 本清单把「超越」拆成**可验收**的条目：每条都写明官方现在的行为、
> Nodio 的目标行为、怎么验证、当前状态。
> 状态取值：**已落地**（有回归锁）/ **进行中** / **待办** / **受限**（物理上做不到）。

---

## S-1 官方预编译块（`=aardio`）**可解释** ✅ 已落地

| | 官方 aardio | Nodio |
| --- | --- | --- |
| 执行自己的预编译块 | ✅ | ❌ 待办（S-1b） |
| 容器结构诊断 | 只给「bad header」/「格式错误」 | 给出对象数 / 记录数 / 常量数 / 嵌套深度 / 记录种类覆盖 / 非法种类数 / 跳转目标可解引用率 |
| 反汇编 | **完全做不到** | `nodio.exe -disasm <file>` 逐条反汇编（官方运行期布局 + 61 种记录语义名） |
| 跳转可解引用性 | 不可见 | 逐条给出落点，并标出越界 |

**验收**：`tests/aardio_chunk_check.ps1`（26 项断言，x64/x86 双绿）。
官方唯一样本 `lib/ide/aifix.aardio` 实测结论：

```
对象: 97   记录: 8734   常量: 2173（字符串 2127 / 数字 42）   最大嵌套: 4
记录种类: 用到 43/61   非法种类: 0   跳转: 631（可解引用 631）
```

> 官方 aardio 连「这个预编译块用了哪 43 种指令、631 个跳转是否都落在指令
> 边界上」都答不出来——它只能执行，不能解释。

**S-1b 预编译块可执行** — 待办。语义已全部取得（`docs/aardio-bytecode.md` §7），
剩下的是把记录流翻译回 Nodio 的 `PNode`（复用现有解释器，比再写一个
aardio VM 风险低）。

## S-2 运行期错误**带文件名与行号** ✅ 已落地

官方 aardio 的运行错误报告是**结构化**的：`aardio.exe` 里存着一整张中英文
字段表（`错误:` / `文件:` / `错误行号:` / `字段:` / `失败操作:` / `匹配行:` …），
配 `aardio：运行时错误` / `aardio：语法错误` / `aardio：内存错误` 这些标题。
也就是说**官方本来就有「文件 + 行号」**——但它躺在 IDE 的多栏报告里，
不是一行能被脚本 / LSP / CI 读走的文本；而且发布时关掉调试
（`dstrip="true"`，官方文档 `docs/guide/ide/file.md`：「错误信息会缺少调试信息
（例如文件名行号）」）就**再也拿不到**。

Nodio 此前只有 `@ 行 155` 一个裸行号——**连官方都有的信息都没有**，
而且那个行号常常属于**被导入的包**而不是正在加载的模块（实测：
`autos.ui.memories` 报 `@ 行 85`，真实根因在 `string\markdown\_.aardio:85`
（加载 32 位 `sundown.dll`），**二分定位花掉一整轮**）。

| | 官方 aardio | Nodio |
| --- | --- | --- |
| 未捕获错误的位置 | 有：结构化报告的 `文件:` / `错误行号:` 两栏 | 有：**一行文本**尾部 `@ <文件>:<行号>` |
| 发布（dstrip）后 | **丢失** | **保留** |
| `catch(e)` 拿到的内容 | `error()` 的原始载荷（官方 `try.md`：「传递给 error 的任何信息都会被 catch 捕获」；官方库 `com/activeX.aardio:63` 直接把 `e` 当错误信息返回） | 载荷 **+ 位置** |
| 位置归谁 | 出错代码所在的文件 | **定义帧**所在的文件：A 的函数被 B 调用 → 报 A |
| 能不能被工具读走 | 不能（弹窗式报告） | 能（一行文本，位置固定在末尾） |

**验收**：
* `tests/vmtests/t13 / t14 / t24` 分别断言「未捕获」「被 `catch` 捕获」
  「调用非函数值」三条出错路径的消息尾部都带 `<脚本>:<行号>`；
* `tests/module_sweep.ps1` 的失败日志可直接按文件归因。

> 附一条实测更正：`@ 行 N` **不是官方格式**——官方二进制里 GBK / UTF-16 /
> UTF-8 三种编码都扫过，`@ 行` 0 命中；那是 Nodio 自己的历史遗留，现已升级为
> `@ <文件>:<行号>`（确实拿不到文件时才回退 `@ 行 N`）。

## S-3 官方库的**自检与归因**能力 ✅ 已落地

官方 aardio 不会告诉你自己的库里有多少模块在 64 位下必然失败。
Nodio 有：

* `tests/module_sweep.ps1` — 969 个公开模块逐个导入；

  且全是「无法加载 DLL」→ 引擎缺陷与物理边界自动分离；
* 失败逐项归因（当前：34 物理边界 / 25 官方契约 / 6 环境超时 / 3 官方库缺依赖 /
  2 `=aardio` / 1 伪模块）。

**验收**：两套架构各自跑完全量，失败集合逐项 diff 为空 → 零回归。

## S-4 双架构构建 ✅ 已落地

官方 aardio 只有 32 位构建，依赖 32 位 DLL 的模块在 64 位环境里无解。
Nodio 同时提供 x64 / x86 构建，让「物理边界」和「真缺陷」能被差分出来
（见 S-3）。官方库里有 34 个模块依赖 32 位 DLL，**只有 Nodio 的 x86 构建能跑它们**。

## S-6 记录流级「Nodio 还缺什么」清单 ✅ 已落地

`=aardio` 的 61 种记录语义已取得（`docs/aardio-bytecode.md` §7.5），
但仍有未决点（类型标签 2 的用途、校验器与解释器对 kind `0x22` 的分歧、
**记录流 → AST 的结构编码**）。

Nodio 目标：在 `-disasm` 输出里直接标出「这些记录种类 Nodio 尚未实现」，
让缺口可量化。

**已落地**：`nodio.exe -disasm <file>` 现在多输出一节
「**== 未实现记录种类 ==**」，逐条列出 61 种记录的操作数角色与语义，
并给出可执行进度：

```
== 未实现记录种类 ==
可执行 0/61（61 种记录全部可解码；本节列出 Nodio 还不能翻译成 AST / 执行的那部分）
  0x05 GET_MEMBER    A=目标 C=键槽 对象=模块命名空间    → 取表成员（走 __get 元方法链）
  0x0B INDEX    A=目标 C=对象槽 B=下标槽    → 按下标取元素（字符串按字符、数组按元素）
  ...
```

这张表是**引擎内的规格表**（`engine/aardio_chunk.cpp` 的 `kKindTable`），
不是文档里的静态表格——S-1b 每落一种，`可执行 N/61` 就跟着涨，
缺口因此始终可量化。

**验收**：`tests/aardio_chunk_check.ps1`（**34 项断言**，x64/x86 双绿）
断言该节存在、列出全部 61 种、并给出操作数角色。

**顺带解掉一个未决点**（第十三轮）：四个 get 变体 / 四个 set 变体的
**操作数角色**已逐 case 确认（§7.5.1）——此前只知道「都调同一个 helper、
但传参不同」。

## S-1b 官方预编译块的**结构校验器** ✅ 第一阶段已落地

官方 aardio 能执行自己的预编译块，但**不能校验、不能诊断**：
它内部确实有校验器（`FUN_004D4450`），却只在加载时跑一次，
失败就抛 `"%s: %s in precompiled chunk"` 然后终止——
用户拿不到「哪个对象的第几条记录违规」这种可定位的结论。

Nodio 把同一套规则做成**产品能力**：

```
== 结构校验 ==
对象 97  记录 8734  违规 0
规则：官方校验器 FUN_004D4450 等价实现（描述符表 DAT_007C80A0 + 操作数寻址 FUN_004D4400 + 跳转配对 + 闭包上值）
结论：通过（官方 aardio 只能执行、给不出这份结构化结论）
```

规则全部实测自官方三处代码：描述符表 `DAT_007C80A0`（每 kind 1 字节）、
操作数检查器 `FUN_004D4400`、校验器 `FUN_004D4450`。等价实现有两套
（`tools/aardio_validate.py` 参考实现 + `engine/aardio_chunk.cpp` 的
`ValidateAardioChunkTree()` 产品实现），在官方唯一样本上**都是 0 违规**。

**这一阶段还解掉了卡了两轮的两个未决点**（`docs/aardio-bytecode.md` §7.8）：

* **常量池寻址约定** ✅ ——常量表在 chunk 帧 `+0x08`（16 字节/项），
  下标有两种载体：9 位操作数 + bit8=1，或 **18 位操作数**（类别 1 的记录）。
  此前把 bit8 误读成「外层作用域标志」；真相是**常量表下标标志**。
* **记录流 → AST 的结构编码** ✅ **该问题被撤销** ——官方运行期根本没有 AST，
  解释器直接执行扁平记录流。所以 Nodio **不需要**把记录流反推成树，
  路线改为「照官方做一个记录 VM」。这让 S-1b 的工作量从「逆向编译器的树形
  编码」降到「实现 61 种记录的寄存器机」，也更忠实。

**验收**：`tests/aardio_chunk_check.ps1`（**38 项断言**，x64/x86 双绿），
断言「结构校验」节存在、计数正确、结论为通过，且 import 阶段的结构化诊断
里带上校验结论。

**下一步**：记录 VM 本体（槽表 / 常量表 / 闭包上值 / 命名空间 / 调用帧），
落地后 `可执行 N/61` 开始上涨。

### S-1b 第二阶段：记录 VM + `nodio.exe -runchunk` ✅ 第一步已落地

第十四轮把**记录 VM 本体**写进了引擎（`engine/aardio_vm.h/.cpp`）：

* 16 字节槽（值 + 官方类型标签 0/1/3/4/6/7）、每 chunk 一份常量表、
  官方操作数寻址（9 位 bit8 = 常量表标志；类别 1 的记录用 18 位常量下标）；
* 已落地 **30 种记录**：取值 / 算术 / 一元负号 / 真值 / 长度 /
  跳转与条件跳转 / 返回 / GC / 位运算；
  `-disasm` 的进度从 `可执行 0/61` 变成 **`可执行 30/61`**
  （进度表在引擎里，随实现自动上涨）；
* 新增 CLI **`nodio.exe -runchunk <file>`**——执行一个官方预编译块并打印结果。
  **官方 aardio 从不提供这种入口**：它只能执行自己编译出来的块。

顺带把「比较跳转的操作数角色」也定案了（§7.5.3）：`A` 不是目标槽，而是
**期望的比较结果**或**真值槽**；`B`/`C` 是比较对象（0x27/0x28 的 `C` 是内联立即数）。

**验收**：`tests/aardio_run_check.ps1`（21 项断言，x64/x86 双绿）——
3+4=7、1..10 求和=55、位运算=49、字符串长度=5、一元负号=-7；
未实现的记录种类**明确报错**（种类 + 记录号，不静默跳过）；
官方真实样本 `lib/ide/aifix.aardio` **优雅失败**（报「尚未实现」而不是崩溃）。

为了让记录 VM 有可验证的样本，新增 `tools/aardio_make_chunk.py`——
按**官方格式文法**合成最小预编译块（官方样本依赖命名空间/闭包/原生函数，
无法单独验证算术与分支语义）。

**下一步**：调用帧与闭包（`0x29`–`0x31`、`0x34`）、命名空间与成员访问
（`0x05`–`0x0D`）、数组与字符串构造（`0x21`、`0x32`）——把剩下的 31 种补齐。

### S-1b 第三阶段：操作数角色定案 + 成员访问族 ✅ 已落地

第十五轮先把**操作数角色**彻底定案，再落成员访问族。

**定案（`docs/aardio-bytecode.md` §7.5.4）**，三路证据互相印证：

* 官方解释器 `FUN_004C4BC0` 调用点的**压栈次序**（cdecl：最后压的才是第 1 实参）；
* 官方校验器 `FUN_004D4450` 里两次 `FUN_004D4400` 的**取位次序**
  （`B` = bits 23..31，类别取自描述符 bits 4..5；`C` = bits 14..22，bits 2..3）；
* 官方唯一样本 `lib/ide/aifix.aardio` 的**交叉验证**（新增 `tools/aardio_ctx.py`
  在样本里定位记录种类并打印上下文与相关常量）。

结论有两条，且都**推翻了第十四轮引擎里的写法**：

1. **二元运算的左操作数恒在 `B`（bits 23..31）**，右在 `C`（bits 14..22）。
   官方样本佐证：`DIV A=6 B=3 C=265!`（`const[9] = 2.0`）= `槽3 / 2.0`。
   → 第十四轮按「`C`=左」写的算术与位运算**左右反了**，本轮改正。
2. **get 与 set 的「对象 / 键」位置并不对称**：
   get（`0x09`/`0x0A`/`0x0B`）是**对象在 `B`、键在 `C`**；
   set（`0x11`/`0x13`/`0x14`）是**对象在 `A`、键在 `B`、值在 `C`**。
   官方样本佐证：`GET_MEMBER3 A=1 B=1 C=268!`（对象=局部槽 1，键=常量 12）
   与 `SET_MEMBER3 A=2 B=282! C=3`（对象=局部槽 2，键=常量 26，值=局部槽 3）。

**落地**：记录 VM 新增**成员访问族** `0x05/0x06/0x07/0x08/0x09/0x0A/0x0B/
0x0C/0x0D/0x10/0x11/0x12/0x13/0x14/0x17` 与 **0x32 BUILD_ARRAY**，
并实现官方表语义：整数键走数组部分（1 基）、字符串键走哈希部分、
命中为 null 时回落到父表（官方表 `+0x08`，引擎侧是新增的 `Table::parent`）。
`-disasm` 的进度从 **`可执行 30/61` 变成 `可执行 46/61`**
（剩 15 种：调用族 / 闭包 / 原生函数 / 导入成员）。

**验收**：`tests/aardio_run_check.ps1` 扩到 **45 项断言**（x64/x86 双绿）：
新增 `sub`(10-3=7)、`div`(9/2=4.5)、`shl`(1<<4=16) 三个**顺序敏感**夹具
（专门锁住左右顺序），以及 `member` / `member2` / `member3` / `index` /
`method` / `array` 六个成员访问族夹具；所有夹具都必须能被官方等价校验器
（`tools/aardio_validate.py`）判为合法。

**下一步**：调用帧与闭包（`0x29`–`0x2B`、`0x2F`–`0x31`、`0x3C`、`0x34`）、
原生函数（`0x15`）与导入成员（`0x16`）——把剩下的 15 种补齐，
让官方唯一样本 `aifix.aardio` 真正跑起来。

### S-1b 第四阶段：调用帧与闭包 ✅ 已落地

第十六轮把「调用族 + 闭包 + 上值」的角色彻底定案，并在记录 VM 里落地。

**定案（`docs/aardio-bytecode.md` §7.5.5）**：

* **调用约定**：被调值 = 槽 `A`；**实参窗口 = 槽 `A+1`..`A+B-1`**（第一个是
  self）；**返回槽 = 槽 `A+B`**（官方 0x2A 装参块 `0x004C5A44` 写
  `vm->0x08 = &slot[A+B]`）；官方另传 `C-1` 作为「实参个数」记进帧 `+0x10`。
* **帧槽布局**：槽 0 = self，槽 1.. = 显式参数；函数体的局部变量与参数
  **共用同一片槽**（官方编译器把局部排在参数之后）。
* **闭包捕获条数 = 嵌套对象的 `flags[0]`**（运行时 chunk 帧 `+0x48`），
  紧随其后的 N 条记录是捕获项（kind 3 = 上值 / kind 4 = 局部槽）并被**消费**。
* **上值按引用**：`FUN_004D5210` 的 cell 指向定义帧的局部槽，
  `0x0E STORE_UPVALUE` 写的就是那个槽。

**官方样本全量自证**：`aifix.aardio` 的 **96 个 `0x34` 记录**逐个校验
「捕获条数 + 后继记录种类」→ **0 违规**。这条自证还纠正了第十五轮的一处
误判（根的子对象是 `/0 /1 /2 /3` 四个，此前把根的 `/1` 误记成 `/0/1`，
才产生「捕获条数矛盾」的假冲突）。

**落地**：记录 VM 改为**帧栈**（每帧独立槽数组，官方是就地压栈），
闭包用 `RtClosure`、上值用 `RtCell`（盒）建模，落地
`0x0E` / `0x0F` / `0x29` / `0x2A` / `0x2B` / `0x34`。
`-disasm` 的进度从 **`可执行 46/61` 变成 `可执行 52/61`**
（剩 9 种：原生函数 / 导入成员 / 字符串拼接 / 复合赋值 / 多值调用）。

**验收**：`tests/aardio_run_check.ps1` 扩到 **58 项断言**（x64/x86 双绿）：
新增 `call`(10)、`params`(7)、`upvalue`(99) 三个调用与闭包夹具，
以及 `recurse`(120) ——闭包先 `SET_MEMBER` 存进模块命名空间、再用
`GET_MEMBER` 取回「自己」递归调用（`f(n) = n * f(n-1)`），
一次跑通「闭包进表 / 从表取回 / 属主命名空间对帧可见 / 嵌套帧」；
`tests/aardio_chunk_check.ps1` 同步到 52 项（x64/x86 双绿）。

### S-1b 第四阶段续：命名空间与导入 ✅ 已落地

第十七轮把「命名空间」这条线读通：`0x15` 建表、`0x16` 导入，
并顺带**纠正**了第十六轮把 VM 暂存槽当成「模块命名空间」的偏差。

**定案（`docs/aardio-bytecode.md` §7.5.6）**：

* **`0x15 NEW_NATIVE` = 新建一张空的命名空间表**（官方 `FUN_004C0810`）：
  type 5、哈希部分与数组部分都是 0、**父表 = 全局内建表 `DAT_007C89B0`**；
  表里的成员由随后的 `0x11 SET_MEMBER3` 填（官方样本根 chunk 记录 39-45
  就是「`NEW_NATIVE A=3` + 6 条 `SET_MEMBER3 A=3`」）。
  > 名字有误导性：0x15 建的**不是函数**，是**表**。
* **`0x16 IMPORT_MEMBER` 的操作数**：**名字 = B 操作数**（bit8=1 → 常量名）、
  **目标槽 = C**、A 不参与。官方描述符 `DAT_007C80A0[0x16] = 0x38`
  （C = 局部槽下标、B = 常量或局部槽）与反汇编 `0x004C62E6` 完全一致。
* **导入行为**（官方 `FUN_004C3B80`）：按 `.` 逐段查表；名字以 `.` 开头则从
  **VM 暂存槽**开始查；查到闭包则取它的**属主命名空间**；
  **查不到就地建一张空命名空间并登记在当前表**；收尾把
  **模块命名空间切到被导入的命名空间**。
* **`vm+0x40` = 全局命名空间**（修正）：官方样本根 chunk 第 0 条
  `GET_MEMBER2` 从 `vm+0x40` 取到的就是**全局函数 `import`**；
  `FUN_004C3B80` 里「绝对路径」的查找起点也是 `vm+0x40`。
  于是：模块命名空间的父表 = 全局命名空间，`0x15` 建出的表父表同理。

**落地**：记录 VM 新增 `globalNs`（全局命名空间）与 `0x15` / `0x16` 两个 case；
`0x16` 的逐段查找覆盖「表 / 闭包属主命名空间 / 查不到就地建表」三条路径。
`-disasm` 的进度从 **`可执行 52/61` 变成 `可执行 54/61`**
（剩 7 种：字符串拼接 / 复合赋值 / 多值与命名空间调用）。

**验收**：`tests/aardio_run_check.ps1` 扩到 **67 项断言**（x64/x86 双绿）：
新增 `new_native`(42)、`import`(42)、`import_new`(7) 三个夹具 ——
分别验证「建表 → 写成员 → 读回」「全局挂模块 → import → 模块命名空间切换」
「导入全局里没有的名字 → 就地建表」；
