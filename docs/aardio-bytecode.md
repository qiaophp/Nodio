
## 2. 文件头（15 字节，已验证）

```

0x00  3D 61 61 72 64 69 6F     "=aardio"
0x07  10 00                    u16 = 16
0x09  01                       版本/标志
0x0A  04 04 04 08 00           头部描述字段
```

**官方证据**：aardio.exe 中校验函数 `FUN_004e9660` 用栈上常量做 16 字节比较：

```c

local_26[1] = '\x10';
local_26[2] = '\0';
local_26[3] = '\x01';
local_26[4] = '\x04';
local_26[5] = '\x04';
local_26[6] = '\x04';
local_26[7] = '\b';
local_26[8] = '\0';
...
if (memcmp(chunk, &local_2c, 15) != 0)
    FUN_004d6330(..., "%s: %s in precompiled chunk", ..., "bad header");
```

比较失败时的官方报错文案是 **"bad header"** 与 **"in precompiled chunk"**，
说明该格式在官方内部的正式名称是 *precompiled chunk*。

> 注：aardio.exe 内部还有 15 字节版本头写入函数 `FUN_004c15b0` /
> `FUN_004c1540`（编译器侧），二者常量一致。

## 3. chunk 递归文法

由官方加载器 `FUN_004e93a0`（解析一个 chunk）及其调用链反编译得到：

```
chunk  :=  name        str          # FUN_004e87a0()
           attr1       i32
           attr2       i32
           flags       u8 × 5
           code        codeBlock     # FUN_004e8880
           consts      constBlock    # FUN_004e8960 (前半)
           objects     objectBlock   # FUN_004e8960 (后半，递归)
           tableA      u32Block      # FUN_004e8df0 (前半)
           tableB      recordBlock   # FUN_004e8df0 (中段)
           tableC      strBlock      # FUN_004e8df0 (后段)

str          := u32 len ; (len-1) 字节 ; u8 flags
                len == 0            -> 空串（null）
                len == strlen + 2
                载荷 = text(strlen) + '\0'，flags & 0x10 表示宽字符
codeBlock    := u32 count ; count × u32      # 指令字，见 §5
constBlock   := u32 count ; count × constant
constant     := u8 type ; 载荷
                type 0 = null   （无载荷）
                type 1 = bool   u8
                type 3 = number 8 字节 IEEE-754 double
                type 4 = string str
                type 2 = 非法，官方报 "bad constant"
objectBlock  := u32 count ; count × chunk
u32Block     := u32 count ; count × u32
recordBlock  := u32 count ; count × (str, i32, i32)
strBlock     := u32 count ; count × str
```

官方加载器用到的错误串（均为 `"%s: %s in precompiled chunk"` 形式）：

| 错误串 | 触发条件 | 出处 |
| --- | --- | --- |
| `bad header` | 15 字节头不匹配 | `FUN_004e9660` |
| `bad constant` | 常量 type 非法 | `FUN_004e8960` |
| `bad integer` | 读到的计数为负 | `FUN_004e8960` / `FUN_004e8df0` |
| `<unexpected end>` | 流提前结束 | `FUN_004e8960` / `FUN_004e8df0` |
| `chunk has too many syntax levels` | 嵌套深度 > 200 | `FUN_004ee510` |
| `chunk has too many lines` | 行数超限 | 编译器侧 |

### 3.1 chunk 的运行时帧布局（第十轮定位）

官方加载器 `FUN_004e93a0` 分配一个 **0x50 字节**的帧对象，按固定顺序读四段数据，
最后**用校验器自己验一遍记录流**（`FUN_004d4450(frame, frame[0x0b], 0xff)`）——
这也解释了官方错误串里的 `in precompiled chunk`：

```
FUN_004e8880(frame)  →  读 code 数组：u32 条数 + count × u32      ← 记录流
FUN_004e8960(frame)  →  读常量池 + 嵌套对象块（递归 chunk）
FUN_004e8df0(frame)  →  读三个并行数据数组（tableA / tableB / tableC）
FUN_004d4450(frame, frame[0x0b], 0xff)  →  校验记录流
```

帧内偏移（每一条都能与官方校验器 `FUN_004d4450` 对上）：

| 偏移 | 含义 |
| --- | --- |
| +0x08 | **常量表指针**（16 字节/项：值 @+0、类型标签 @+8）——校验器按 `+8 + idx*0x10` 取表项，成员名类记录要求表项类型必须是 4（字符串） |
| +0x0C | **code 数组指针**（记录流；校验器逐条取记录） |
| +0x10 | 嵌套对象表指针（`NEW_CLOSURE` 按它取闭包体） |
| +0x14 / +0x30 | tableA 指针 / 条数（u32Block，字面量） |
| +0x18 / +0x38 | tableB 指针 / 条数（每项 12 字节 = name + i32 + i32） |
| +0x1C / +0x24 | tableC 指针 / 条数（strBlock，字符串常量） |
| +0x28 | **常量数**（校验器按它收口「常量下标」类操作数） |
| +0x2C | code 条数（= `frame[0x0b]`，校验器的 `param_2`） |
| +0x34 | 嵌套对象数（`NEW_CLOSURE` 的对象下标上界；> 200 报 `chunk has too many syntax levels`） |
| +0x48 | upvalue 数量上限（校验 kind 0x03 / 0x0E 的上值下标） |
| +0x4A | 标志字节（bit1 = 允许 kind 0x3C，bit2 = 禁止 kind 0x3C） |
| +0x4B | **局部槽数**（校验器要求「目标槽 A < 它」；实测 `maxA + 1 == 槽数`） |
| +0x3C / +0x40 | **源码首行 / 末行**（chunk 头的两个 i32；实测随嵌套顺序单调递增、区间不重叠） |

**这解释了 §5 的操作数字段**：记录的「槽位索引」类操作数必须小于 `+0x4B`
（局部槽数），「常量索引」类必须小于 `+0x28`（常量数），
「相对位移」类按当前记录位置计算——三者都依赖这个帧。

固化位置：`tools/aardio_vm_tables.py` 的 `CHUNK_FRAME_LAYOUT` /
`CHUNK_LOADER_STEPS`。

## 5. 记录编码（32 位记录流）

> ⚠️ **第九轮修正**：本节原先把这条 32 位字称作「RISC 指令」。定位到 VM 主分派
> `FUN_004ec700` 与记录发射器 `FUN_004f5b20` 后确认：官方 VM 是
> **AST 树遍历 + 记录流**两层结构，这条字是**记录**（record），不是机器指令。
> 记录种类（bits 0..5）决定操作数格式；C 段/B 段在运行期被回填为
> **表达式项数 / 语句数**。详见 §6.5。其余字段布局与下述一致。

一条记录 = 一个 u32：

```
bit 31..23   C   (9 bit)
bit 22..14   B   (9 bit)
bit 13..6    A   (8 bit)
bit  5..0    opcode (6 bit, 0x00..0x3C)
```

官方解码器 `FUN_004d4450` 的反编译片段：

```c
uVar3 = *(uint *)(iVar4 + local_8 * 4);   // 取指令字
uVar6 = uVar3 & 0x3f;                      // opcode
uVar8 = uVar3 >> 6 & 0xff;                // 操作数 A
bVar1 = (&DAT_007c80a0)[uVar6];            // 操作数格式描述符
if ((bVar1 & 3) == 0) {
    local_c = uVar3 >> 0xe & 0x1ff;        // 操作数 B (9 bit)
    uVar9  = uVar3 >> 0x17;               // 操作数 C (9 bit)
} else if ((bVar1 & 3) == 1) {
    uVar9 = uVar3 >> 0xe;                  // 18 bit 操作数
} else if ((bVar1 & 3) == 2) {
    uVar9 = (uVar3 >> 0xe) - 0x1ffff;      // 18 bit 有符号（PC 相对）
}
```

### 5.1 记录种类的操作数格式描述符表

`DAT_007c80a0`（aardio.exe 内存 VA `0x007C80A0`，**64 字节**，每个记录种类 1 字节）：

```
71 54 60 50 60 71 41 71  60 6c 6c 6c 31 31 10 20
30 3c 3c 3c 3c 54 38 6c  7c 7c 7c 7c 7c 7c 60 60
60 68 22 bc bc bc bc e4  e4 28 54 54 10 62 62 84
00 84 14 00 51 70 7c 7c  7c 7c 7c 50 00 00 00
```

> ⚠️ **第十轮修正**：本节原先的位含义是早期推断，与官方校验器 `FUN_004d4450`
> 的实际取操作数代码逐条对不上。下面是按校验器代码重新解码的结果。

| 位 | 含义（校验器 `FUN_004d4450` 的实际取法） |
| --- | --- |
| 0..1 | 操作数格式类：`0` = 双操作数（A = bits14..22 共 9 位，B = bits23..31 共 9 位）；`1` = 单操作数（bits14..31 共 18 位，无符号）；`2` = 单操作数（bits14..31 再减 `0x1FFFF`，18 位**有符号**）；`3` 未使用 |
| 4..5 | `0x30` = 该操作数是**槽位索引**，必须小于 chunk 帧槽位上限（校验器读 `param_1+0x28`）；`0x20` = 该操作数是**相对位移**（相对当前记录位置）；`0x10` 单独出现时校验器不做额外检查 |
| 6 | 该记录**可以作为控制流跳转目标**（校验器：`(&DAT_007c80a0)[kind] & 0x40` 且被查询的 pc 等于当前 pc 时，把 pc 记为分支目标） |
| 7 | 该记录**必须紧跟一条 0x22 跳转记录**（校验器检查 `code[pc+1]` 的种类必须等于 `0x22`，否则整个 chunk 判为非法） |

**合法记录种类只有 61 种**（`0x00`..`0x3C`）：校验器开头就是
`if (0x3c < uVar6) return 0;`，`0x3D`..`0x3F` 三个槽位是 0 且被直接拒绝。
「64 种」的说法来自种类字段占 6 位（bits0..5），实际取值空间是 61。

| 0x10 | 0x0E, 0x2C | 双 | — |
| 0x14 | 0x32 | 双 | — |
| 0x20 | 0x0F | 双 | 相对位移 |
| 0x22 | 0x22 | 单（有符号） | 相对位移 |
| 0x28 | 0x29 | 双 | 相对位移 |
| 0x30 | 0x10 | 双 | 槽位索引 |
| 0x31 | 0x0C, 0x0D | 单 | 槽位索引 |
| 0x38 | 0x16 | 双 | 槽位索引 |
| 0x3C | 0x11–0x14 | 双 | 槽位索引 + 可跳转目标 |
| 0x41 | 0x06 | 单 | 可跳转目标 |
| 0x50 | 0x03, 0x3C | 双 | 可跳转目标 |
| 0x51 | 0x34 | 单 | 可跳转目标 |
| 0x54 | 0x01, 0x15, 0x2A, 0x2B | 双 | 可跳转目标 |
| 0x60 | 0x02, 0x04, 0x08, 0x1E–0x20 | 双 | 相对位移 + 可跳转目标 |
| 0x62 | 0x2D, 0x2E | 单（有符号） | 相对位移 + 可跳转目标 |
| 0x68 | 0x21 | 双 | 相对位移 + 可跳转目标 |
| 0x6C | 0x09–0x0B, 0x17 | 双 | 相对位移 + 可跳转目标 |
| 0x70 | 0x35 | 双 | 槽位索引 + 可跳转目标 |
| 0x71 | 0x00, 0x05, 0x07 | 单 | 槽位索引 + 可跳转目标 |
| 0x7C | 0x18–0x1D, 0x36–0x3B | 双 | 槽位索引 + 可跳转目标 |
| 0x84 | 0x2F, 0x31 | 双 | 必须紧跟 0x22 |
| 0xBC | 0x23–0x26 | 双 | 槽位索引 + 必须紧跟 0x22 |
| 0xE4 | 0x27, 0x28 | 双 | 相对位移 + 可跳转目标 + 必须紧跟 0x22 |

「必须紧跟 0x22」的 **14 个种类**是**条件跳转类**：自身携带条件/目标信息，
真正的位移由紧跟其后的 `0x22` 记录给出（`0x22` 是唯一的有符号相对位移形态）。
`0x2D` / `0x2E` 是例外——它们自己就带位移，同时又允许作跳转目标。

固化位置：`tools/aardio_vm_tables.py` 的 `OPERAND_DESC_BYTES` /
`RECORD_SHAPE_GROUPS` / `check_shape_groups()`（自带覆盖自检：61 个合法种类
必须每个出现且只出现一次，形态字节必须与描述符表一致）。

### 5.3 已知语义

* `opcode 0x22` = 跳转记录：唯一的有符号相对位移形态，位移 = `(word >> 14) - 0x1FFFF`，
  目标 = `pc + 1 + 位移`。
* `opcode 0x28` = **条件跳转**（形态 0xE4：双操作数 + 相对位移位 + 可作跳转目标 +
  必须紧跟 0x22）——条件与目标信息在自身，位移在紧随的 `0x22`。
  证据：编译器优化器 `FUN_004f4030` 用 `((param_2 - in_EDX) + 0x1fffe) * 0x4000`
  重写 `0x22` 记录的那个字段。
* `opcode 0x32` = 指令流标记（形态 0x14；校验器对 `C==0` 特殊处理）。
* 完整 61 种记录各自的**运行期语义**仍未逐一还原，需要继续反编译语句解释器的分派表。

## 6. 表达式求值层

除指令流外，chunk 还带一棵表达式/节点树，求值器为 `FUN_004ee510`：

```c
switch(*(undefined4 *)(param_1 + 0x14)) {   // 节点类型
```

### 6.4 官方校验器给出的 opcode 结构约束（20/64）

官方 chunk 校验器 `FUN_004d4450` 对每个 opcode 做了**形式化校验**，
这些约束反过来说明了各 opcode 的操作数含义。已还原的约束见
`tools/aardio_vm_tables.py` 的 `OPCODE_CONSTRAINTS`（按 opcode 索引）。

值得单独指出的几条：

* `0x05 / 0x07 / 0x0c / 0x0d`：操作数 B 索引的表项，其类型字段必须为 `4`
  → 说明 B 是「命名空间/表项索引」。
* `0x34`：操作数 C 指向一个计数，后续必须紧跟 `count` 条 opcode 为 `3`/`4` 的指令
  → 说明这是一条「批量局部变量声明」。
* `0x3c`：受 chunk 标志位约束（`flags & 2` 必须置位、`flags & 4` 必须清零）
  → 这是 chunk 级别的结束/返回类指令。
* `0x22`：跳转目标 = `pc + 1 + C`；`0x2d/0x2e` 额外要求 `A+3` 是合法局部变量编号。

### 6.5 VM 主分派与「记录」模型（第九轮重大修正）

第九轮定位到官方 VM 的主分派循环 **`FUN_004ec700`**（1489 字节）与**记录发射器
`FUN_004f5b20`**，据此**修正**了 §5 的表述：官方 VM 不是「RISC 指令流解释器」，
而是 **AST 树遍历 + 记录流（record stream）** 两层结构。

**记录发射器 `FUN_004f5b20(kind, dest)`**：

```c
*(undefined4 *)(*(int *)(iVar1 + 0xc) + slot * 4) = param_1;   // code 数组
*(undefined4 *)(*(int *)(iVar1 + 0x14) + slot * 4) = param_2;  // 并行数据数组
unaff_ESI[6] = unaff_ESI[6] + 1;                               // slot++
```

即：每条记录 = 一个 32 位字（写入 code 数组）+ 一个 32 位辅助字（写入并行数组），
发射后立即调用 `FUN_004f4030` 做分支重定位。

**主分派 `FUN_004ec700`**（关键片段）：

```c
uVar9 = *(undefined4 *)(in_ECX + 0x14);        // 当前 AST 节点类型
switch(uVar9) {
case 0x40:  FUN_004ebe80(); break;            // 专用节点
case 0x5b:  FUN_004ebf50(); break;
case 0x108: FUN_004d6820(); break;            // 错误
default:    FUN_004ee510(); ... break;         // 表达式求值（运算符分派）
case 300: case 0x12f: case 0x12e: case 0x131: ...   // 复合节点
}
...
/* 回填：表达式项数进 C 段，语句数进 B 段 */
*(uint *)(*(int *)(*piVar3 + 0xc) + iVar5 * 4) =
     *(uint *)(*(int *)(*piVar3 + 0xc) + iVar5 * 4) & 0x7fffff | uVar10 << 0x17;   // C 段
*puVar1 = *puVar1 ^ (uVar10 << 0xe ^ *puVar1) & 0x7fc000;                          // B 段
```

**结论（观察，非推断）**：

* 记录字的 bits 23..31（C 段）存的是**表达式项数**，bits 14..22（B 段）存的是**语句数**，
  两者都是官方自定义的 varint 编码（写入前用 `x = i*8+8 | x-8` 归一）；
* bits 0..5 是**记录种类**（0..0x3c），`DAT_007c80a0` 描述的是这个字段的**操作数格式**；
* 节点类型在运行期结构体偏移 `+0x14`，三个子节点槽在 `+0x24 / +0x28 / +0x2c`；
  父/兄弟指针在 `+0x04 / +0x08`；递归深度计数器在 `+0x34`（上限 200，对应官方报错
  `"chunk has too many syntax levels"`）。

> 这解释了为什么官方调试器 `FUN_004d4940` 能按「pc」反查变量类别：pc 就是
> code 数组下标，调试器把该下标处的记录解出来，看种类就知道读的是
> local / upvalue / field / method。

## 7. 官方运行期记录解释器（第十一轮定位）

### 7.1 定位

```
FUN_004C4BC0   @ 0x004C4BC0   size = 7263 bytes
```

它是整个 `aardio.exe` 里**唯一**一处对 32 位记录做 `switch (word & 0x3F)` 的函数：

* 分派语句是 `switch(uVar19 & 0x3f)`，case 覆盖 `0x00`–`0x3C` **全部 61 种**，
  与 chunk 校验器 `FUN_004D4450` 的 `if (0x3C < kind) return 0;` 完全吻合；
* 循环体每轮 `word = *IP; IP++`，与 §3.1 的 code 数组布局吻合；
* 两个调用入口：`FUN_004D33C0`（带 C 栈溢出检查，上限 200 层）与 `FUN_004D3450`。

由此可以确认：**官方 `=aardio` 就是「32 位 RISC 记录流 + 一个寄存器机解释器」**，
不存在第二套语义层。第九轮那句「官方 VM 不是 RISC 指令流解释器」的说法
（基于 `FUN_004EC700` 遍历 AST 节点树）只对**编译器侧**成立——`FUN_004EC700`
是编译期的 AST 遍历器，运行期解释器是 `FUN_004C4BC0`。

### 7.2 记录字位布局（实测自解释器自身的取位表达式）

```
bits  0.. 5 : kind     (6 bit)   0x00..0x3C
bits  6..13 : A        (8 bit)   目标局部槽（< 槽位数）
bits 14..22 : C        (9 bit)   操作数①（bit22=1 时指常量表）
bits 23..31 : B        (9 bit)   操作数②（bit31=1 时指常量表）
```

> ⚠️ **第十三轮修正**：本节原先把第 9 位（bit22 / bit31）写成
> 「全局作用域标志」，并把 bits 14..31 一律当成「两个 9 位操作数」。
> **这是错的**，实测证据见 §7.5.2：
>
> * **9 位操作数**（C / B）的第 9 位决定寻址方式：
>   `0` → **局部槽下标**，`1` → **常量表下标**；
> * **18 位操作数**（bits 14..31 合成）在「描述符类别 1」的记录上是
>   **常量表下标**（成员名）或**嵌套对象下标**（闭包体）——
>   正是它让一个 chunk 能引用 963 个常量（9 位下标最多只能到 511）。

**跳转类记录**（`0x22`/`0x23`/`0x24`/`0x25`/`0x26`/`0x27`/`0x28`/`0x2D`/`0x2E`）
把 bits 14..31 当成**一个 18 位有符号相对位移**用，但**位移取自哪一条记录、
偏置是多少，各不相同**（实测自解释器的取位表达式）：

| kind | 位移取自 | 偏置 | 落点 |
| --- | --- | --- | --- |
| `0x22` / `0x2D` / `0x2E` | 本条记录 | `0x1FFFE` | `pc + (raw - 0x1FFFE)` |
| `0x23` / `0x24` / `0x25` / `0x26` | **下一条** u32 | `0x1FFFE` | `pc + (raw_next - 0x1FFFE)` |
| `0x27` / `0x28` | **下一条** u32 | `0x1FFFD` | `pc + (raw_next - 0x1FFFD)` |

条件跳转（`0x23`–`0x28`）读的「下一条 u32」就是编译器紧跟其后的一条 `0x22`
（校验器也强制「带符号操作数的记录后面必须紧跟一条 0x22」）。
未命中时 `IP = pc + 2`（跳过那条 `0x22`）。

`0x27`/`0x28` 的偏置比 `0x23`–`0x26` 少 1，正好使「条件跳转的落点」与
「紧跟的 0x22 自己的落点」相同——官方样本里可以直接验证：

```
 14  00004027  JTRUE   A=0 B=0 C=1                    ; rel18=21(next) -> 35
 15  80048022  JMP     A=0 B=0 C=18                   ; rel18=20(own)  -> 35
```

两条记录落在同一个 `35`，模型自洽。

**全样本验证**：`python tools/aardio_vm_runtime.py D:\aardio\lib\ide\aifix.aardio`
对官方样本全部 97 个对象逐条扫描，得到
**条件跳转 / 0x22 配对 228 对，落点不一致 0 处** → 位布局、位移来源、偏置
三项一起被样本独立验证。

### 7.3 运行时槽位（16 字节）与类型标签

```
+0x00  值        （type 1/3 是 8 字节值；type 3 按 double 解释）
+0x08  类型标签
+0x0C  附加      （type 4 是字符串长度；type 6/7 是对象指针）
+0x10  附加 2    （type 4 是字符串数据指针）
```

类型标签（由 `FUN_004C30A0` / `FUN_004C3700` 按 tag 分派实测；基本类型槽位在
`heap + 0x98 + tag * 4`）：

| tag | 含义 | 值位置 |
| --- | --- | --- |
| 0 | null | — |
| 1 | bool（整数 0/1） | +0x00 |
| 2 | int（推断：走基本类型槽位，具体用途未定位） | — |
| 3 | number（double） | +0x00 |
| 4 | string | 长度 +0x0C，数据 +0x10 |
| 5 | namespace / 类表（自带哈希表） | +0x0C |
| 6 | function / 闭包 | +0x0C |
| 7 | table | +0x0C |

### 7.4 VM 状态对象与调用帧

解释器的 `this`（反编译里的 `in_EAX`）字段：

| 偏移 | 含义 |
| --- | --- |
| +0x08 | 值栈顶指针（指向当前槽位） |
| +0x0C | 当前帧局部槽表基址 |
| +0x10 | 运行时上下文（堆）指针 |
| +0x14 | 调用帧栈指针（每帧 0x18 字节） |
| +0x18 | **指令指针 IP**（指向记录流中的当前 u32） |
| +0x1C / +0x20 | 值栈上界 / 基址 |
| +0x24 / +0x28 / +0x2C | 调用帧栈上界 / 基址 / 计数 |
| +0x34 | 调用深度（ushort，上限 200） |
| +0x36 | 标志字节（bit0 = 跟踪，bit1 = 断点） |
| +0x40 | 父帧 / 原生宿主 |

调用帧（0x18 字节，由 `FUN_004D3040` 建立）：

| 偏移 | 含义 |
| --- | --- |
| +0x00 | 新帧局部槽表基址 |
| +0x04 | 实参区基址 |
| +0x08 | 局部槽表上界 |
| +0x0C | 记录流（code）基址 |
| +0x10 | self |
| +0x14 | 帧计数 |

**调用约定**（第十六轮按 `FUN_004D3040` 与 0x2A 装参块重新读出）：

* **被调值在调用者的槽 `A`**（`FUN_004D3040` 的 `in_EAX` = `&slot[A]`）；
* **实参窗口 = 槽 `A+1` .. `A+B-1`**（共 `B-1` 个值，第一个是 self / 接收者）：
  官方原生调用路径把 `[&slot[A], &slot[A+B])` 整段复制到新帧（`0x2B` 分支的
  `puVar9 < vm->0x08` 循环），被复制的正是 `A+1..A+B-1` 这些值；
* **返回槽 = 槽 `A+B`**：`0x2A` 装参块（`0x004C5A44`）在 `B != 0` 时写
  `vm->0x08 = &slot[A+B]`；
* 官方传给被调方的「实参个数」= `C-1`（`C == 0` 时为 `-1`，即变参），
  记在调用帧 `+0x10`；
* **帧槽布局**：槽 0 = self，槽 1.. = 显式参数；函数体的局部变量与参数**共用
  同一片槽**（官方编译器把局部排在参数之后）——由官方样本 `/0/0` 的
  `LOAD_LOCAL B=1`（第一个显式参数）与 `/0/1` 的 `LOAD_LOCAL B=2` 佐证；
* 官方是**就地压栈**（被调帧直接覆盖调用者的 A+1.. 槽），Nodio 用「每帧独立
  槽数组」实现，语义等价。

算术与位运算两组是**强证据**：它们分别走两个专用 helper，且 helper 的分派参数
就是 opcode 本身——

* `FUN_004C4740`（二元算术）按 `opcode - 0x12` 分派：
  `6=+ 7=- 8=* 9=/ 10=% 11=^ 12=一元负号`，
  对应 `0x18..0x1E`；
* `FUN_004C49C0`（位运算）按 opcode 本身分派：
  `0x35=~ 0x36=& 0x37=| 0x38=^ 0x39=<< 0x3A=>> 0x3B=>>>`。

两者在解释器里都有「双槽都是 number 时的快速路径」，慢路径回落到 helper，
helper 再回落到元方法（`FUN_004C3DB0`，`__add`/`__sub`/…）。

### 7.5.1 操作数角色（第十三轮补全）

§7.2 的位布局只说了「哪几段是操作数」，没说**每种记录里每个操作数是什么角色**。
第十三轮把官方解释器 `FUN_004C4BC0` 的反汇编（`tools/ghidra/DumpDisasm.java`
新导出，见 §11）逐 case 读了一遍，helper 调用前的寄存器布置全部确认：

| 段 | 含义 |
| --- | --- |
| `A` = bits 6..13（8 bit） | **目标槽**（局部槽表里的下标；槽宽 16 字节 = 12 字节值 + 4 字节类型标签） |
| `C` = bits 14..22（9 bit） | **操作数①**；bit22 = 1 → 该下标指向**常量表**，否则指向**局部槽表** |
| `B` = bits 23..31（9 bit） | **操作数②**；bit31 = 1 → 同上（指常量表） |
| `K` = bits 14..31 合成（18 bit） | **描述符类别 1** 的记录唯一操作数：常量表下标 / 嵌套对象下标 |
| `R18` = bits 14..31 合成 | 跳转类的 18 位相对位移 |

> ⚠️ **第十三轮修正**：此表原先写的是「bit22/bit31 = 外层作用域」，
> 「0x05/0x07/0x0C 的 C = 键槽」。**两处都是错的**：
> 那个第 9 位是**常量表下标标志**（§7.5.2 有决定性证据），
> 而 0x05/0x07/0x0C/0x0D 的操作数是 **18 位常量下标**（成员名字符串常量），
> 不是「槽」。

由此**逐个确认了 §7.8 里悬着的 get/set 变体**（此前只知道「都调同一个 helper、
但传参不同」）：

| kind | 名称 | 角色 | helper |
| --- | --- | --- | --- |
| 0x05 | GET_MEMBER | `A`=目标，`K`=**常量下标（成员名）**，对象 = **模块命名空间**（type 5） | `FUN_004C30A0` flag=0 |
| 0x07 | GET_MEMBER2 | `A`=目标，`K`=**常量下标（成员名）**，对象 = **VM 暂存槽**（`+0x40`） | `FUN_004C30A0` flag=0 |
| 0x09 | GET_MEMBER3 | `A`=目标，`B`=**对象槽**，`C`=**键槽**（bit22=1 → 常量名） | `FUN_004C30A0` flag=-1 |
| 0x0A | GET_MEMBER4 | 同 0x09 | `FUN_004C30A0` flag=0 |
| 0x0B | INDEX | `A`=目标，`B`=**对象槽**，`C`=**下标槽** | 内联处理 + `FUN_004C0B40` |
| 0x0C | SET_MEMBER | `A`=**值槽**，`K`=**常量下标（成员名）**，对象 = 模块命名空间 | `FUN_004C3700` flag=1 |
| 0x0D | SET_MEMBER2 | `A`=**值槽**，`K`=**常量下标（成员名）**，对象 = VM 暂存槽 | `FUN_004C3700` flag=1 |
| 0x11 | SET_MEMBER3 | `A`=**对象槽**，`B`=**键槽**，`C`=**值槽** | `FUN_004C3700` flag=1 |
| 0x14 | SET_MEMBER4 | 同 0x11 | `FUN_004C3700` flag=0 |

helper 的调用约定（从 `PUSH` 顺序读出，cdecl 右到左）：
`FUN_004C30A0(vm, 对象槽, 键槽, 结果槽, flag)`、
`FUN_004C3700(vm, 对象槽, 键槽, 值槽, flag)`。
其中「模块命名空间」是**栈上临时拼的 12 字节槽**（值 = 帧的命名空间指针，
类型标签 = 5），不是槽文件里的某一格——这也是 0x05/0x0C 与 0x09/0x0D 的
真正区别。

> ⚠️ **第十五轮修正**：上表里 0x09/0x0A/0x0B 的「`C`=对象槽、`B`=键槽」
> 与 0x11/0x14 的「同 0x0D」**都是错的**（详见 §7.5.4）：
> get 家族是「对象在 B、键在 C」，set 家族是「对象在 A、键在 B、值在 C」，
> 而 `FUN_004C30A0` 的第 2 实参是**对象**、第 3 实参才是**键**
> （`param_2[2]==4 && *(int*)(param_3+1)==3` 这一句就是「对象是字符串、
> 键是数字」的判定）。第十三轮那张表把两个 helper 的实参顺序记反了。

**这套角色表已经进引擎**（`engine/aardio_chunk.cpp` 的 `kKindTable`），
`-disasm` 会把「未实现记录种类」整节打出来（见 §10）。

### 7.5.2 描述符表与操作数寻址（第十三轮决定性突破）

S-1b 之前有两个未决点卡住：**常量池寻址约定**、**操作数的两种寻址方式**。
第十三轮把官方的**三处代码**对上了，两个未决点一起解开：

| 官方代码 | 作用 |
| --- | --- |
| `DAT_007C80A0`（64 字节描述符表） | 决定**每种记录的操作数格式** |
| `FUN_004D4400`（操作数检查器） | 决定**9 位操作数指向哪张表** |
| `FUN_004D4450`（记录流校验器） | 逐条记录的结构约束 |

**描述符表**每 kind 1 字节，位含义（自 `FUN_004D4450` 的取位表达式读出）：

| 位 | 含义 |
| --- | --- |
| bits 0..1 | 记录类别：`0`=三操作数(A,C,B)、`1`=单 18 位操作数(K)、`2`=单 18 位有符号(位移) |
| bits 2..3 | **C 操作数的寻址类别** |
| bits 4..5 | **B 操作数**（类别 1 时即 K）的寻址类别 |
| bit 6 | 可作为断点落点 |
| bit 7 | 负号位：该记录后必须紧跟一条 `0x22` |

**寻址类别**（`FUN_004D4400` 的三个分支）：

| 类别 | 语义 |
| --- | --- |
| 0 | 操作数**必须为 0** |
| 1 | 不检查（立即数 / 内建序号 / 计数等） |
| 2 | **局部槽下标**，必须 < 槽位数（chunk 帧 `+0x4B`） |
| 3 | **bit8 = 1 → 常量表下标**（< 常量数，帧 `+0x28`）；**bit8 = 0 → 局部槽下标** |

于是两个未决点的答案：

1. **常量池寻址约定**：常量表在 chunk 帧 `+0x08`，**16 字节/项**
   （值 8 字节 @+0、类型标签 @+8），常量数在 `+0x28`。
   常量下标有两种载体：
   * 9 位操作数 + bit8=1（最多 256 个）——用于 `C`/`B` 位置；
   * **18 位操作数 K**（最多 262143 个）——用于 `0x00/0x05/0x07/0x0C/0x0D`
     （成员名等字符串常量）与 `0x34`（嵌套对象下标）。
   官方样本 `aifix.aardio` 的主对象有 **963 个常量**——9 位根本不够，
   正是靠 18 位操作数才引用得下（`LOAD_OUTER` 一条就用了 2128 次）。
2. **「记录流 → AST 的结构编码」**这个问题本身要撤销：官方运行期**根本没有
   AST**，它执行的就是这串扁平记录（解释器 `FUN_004C4BC0` 只认记录流）。
   所以 Nodio 要执行官方预编译块，**不需要**把记录流反推成树——
   正确路线是**照官方做一个记录 VM**（槽表 + 常量表 + 闭包 + 命名空间）。
   这比「反推 AST」更短、也更忠实（AST 反推必然有损）。

**独立验证**：把上述规则写成两套等价实现——

* `tools/aardio_validate.py`（Python 参考实现）
* `engine/aardio_chunk.cpp` 的 `ValidateAardioChunkTree()`（产品实现）

两者在官方唯一样本 `lib/ide/aifix.aardio` 上都给出 **0 违规**（97 个对象 /
8734 条记录 / 631 个跳转），说明规则本身自洽且被样本独立验证。

### 7.5.3 记录 VM：官方比较跳转的操作数角色（第十四轮补全）

条件跳转这一族此前只知道「位移取自下一条 u32」，**比较的是哪两个槽、
以及 `A` 是什么**，一直悬着。第十四轮把官方解释器
`FUN_004C4BC0` 的 case 0x23–0x28 与三个比较 helper 对上后定案：

| kind | 名称 | `A` | `B` | `C` | 语义 |
| --- | --- | --- | --- | --- | --- |
| 0x23 | JZ | **期望的布尔结果(0/1)** | 左操作数 | 右操作数 | `r = (B == C)`（`FUN_004C41F0`，带元方法链）；`r == A` 时跳转 |
| 0x24 | JE | 同上 | 左 | 右 | `r = (B == C)`（内联快路径）；`r == A` 时跳转 |
| 0x25 | JG | 同上 | 左 | 右 | `r = (C > B)`（`FUN_004C40F0`）；`r == A` 时跳转 |
| 0x26 | JLE | 同上 | 左 | 右 | `r = (B <= C)`（`FUN_004C4160`）；`r == A` 时跳转 |
| 0x27 | JTRUE | **真值槽** | — | **立即数(0/1)** | `真值(槽A) != C` 时跳转 |
| 0x28 | JTRUE2 | 目标槽 | **真值槽** | **立即数(0/1)** | `真值(槽B) != C` 时跳转，并令 `A ← 槽B` |

要点：

* `A` 在这一族里**不是目标槽**，而是「期望的比较结果」或「真值槽」——
  官方代码是 `CMP EAX, [ESP+0x3c]`，而 `[ESP+0x3c]` 就是 `A`；
* `B`/`C` 在 0x23–0x26 是**槽或常量**（各自 bit8 决定），
  在 0x27/0x28 里 `C` 是**内联立即数**（9 位），不是槽；
* 这解释了为什么 0x23 与 0x24 长得几乎一样：官方一个走 helper
  （带 `__eq` 元方法链），一个走内联快路径。

### 7.5.4 操作数角色（第十五轮定案：左操作数在 B、对象与键不对称）

第十四轮把算术/位运算的**左右顺序**在引擎里落地时用的是「`C`=左、`B`=右」。
第十五轮按官方解释器的**调用点装参序列**逐条复核，发现这个约定整体**反了**，
连带 get/set 家族的「对象槽 / 键槽」位置也反了。本节是定案记录。

#### 7.5.4.1 字段名 B/C 的归属（不变）

官方校验器 `FUN_004D4450` 里两次调用 `FUN_004D4400`（9 位操作数检查器）
的取位顺序给出了字段归属：

```
004d4581  MOV EAX,EDI        ; EDI = 描述符字节
004d4583  SHR EAX,0x4        ; → bits 4..5
004d4586  SHR ESI,0x17       ; ESI = 记录 >> 23 = bits 23..31
004d4589  AND EAX,0x3
004d458c  MOV ECX,ESI
004d458e  CALL 0x004d4400    ; 检查 bits 23..31，类别取自描述符 bits 4..5
...
004d459d  MOV EAX,EDI
004d459f  SHR EAX,0x2        ; → bits 2..3
          AND EAX,0x3
          CALL 0x004d4400    ; 检查 bits 14..22，类别取自描述符 bits 2..3
```

即：**`B` = bits 23..31**（类别在描述符 bits 4..5）、
**`C` = bits 14..22**（类别在描述符 bits 2..3）。这条第十四轮已定，本轮不变。

#### 7.5.4.2 左操作数恒在 B（bits 23..31）

| 记录 | 官方证据 | 结论 |
| --- | --- | --- |
| 0x19 SUB | `decomp` 345-349：`dVar2 = *pdVar12; dVar1 = *pdVar17;` → `*pdVar12 - *pdVar17`，其中 `pdVar12` 取自 `uVar19 >> 0x17`（= B）、`pdVar17` 取自 `(uVar19 >> 0xe) & 0x1ff`（= C） | `A ← B - C` |
| 0x1B DIV | `decomp` 399-403：同上取位 → `*B / *C` | `A ← B / C` |
| 0x1C MOD | `decomp` 426-431：`*B - fmod(*C)` | `A ← B % C` |
| 0x1D POW | `decomp` 454-456：`FUN_007498A0(*B, *C)` | `A ← B ^ C` |
| 0x36/37/38/3B、0x39/3A | `disasm` 0x004C62C1-0x004C62C6：`PUSH ECX(种类) / PUSH EAX(C 段槽) / PUSH ESI(B 段槽) / PUSH EDI(目标槽) / PUSH EBX(vm)` → `FUN_004C49C0(vm, dest, *B, *C, kind)`；而 `FUN_004C49C0` 里 `local_10 = *param_3(=B)`、`uVar4 = *param_4(=C)` | `A ← B & C` / `B \| C` / `B ^ C` / `B << C` / `B >> C` |

官方样本交叉验证（`lib/ide/aifix.aardio`）：

```
=== /0/13  pc=47  DIV  A=6 B=3 C=265!
    const[C=9] = 2.0
```

`B`=局部槽 3、`C`=常量 2.0 → `槽6 = 槽3 / 2.0`（除数在右）✓ 与上表一致。

> ⚠️ 这条同时推翻了 Nodio 记录 VM 第二阶段的实现：当时按「`C`=左、`B`=右」
> 写的算术与位运算**左右反了**。第十五轮已改正，并补了
> `sub` / `div` / `shl` 三个**顺序敏感**的合成夹具来锁住它。

#### 7.5.4.3 get 与 set 的「对象 / 键」位置并不对称

压栈次序（cdecl：最后压的才是第 1 实参）：

```
get（0x09/0x0A/0x0B）:  PUSH flag(-1) / PUSH dest(A) / PUSH key(C) / PUSH obj(B) / PUSH vm
set（0x11/0x13/0x14）:  PUSH flag     / PUSH value(C) / PUSH key(B) / PUSH obj(A) / PUSH vm
```

* `FUN_004C30A0(vm, obj, key, dest, flag)`：第 2 实参是**对象**、第 3 实参是**键**
  （`param_2[2]==4 && *(int*)(param_3+1)==3` = 「对象是字符串、键是数字」）。
* `FUN_004C3700(vm, obj, key, value, flag)`：第 2 实参是**对象**、第 3 实参是**键**、
  第 4 实参是**值**。

于是：

| kind | 名称 | A | B | C |
| --- | --- | --- | --- | --- |
| 0x09/0x0A | GET_MEMBER3/4 | 目标 | **对象槽** | **键槽**（bit22=1 → 常量名） |
| 0x0B | INDEX | 目标 | **对象槽** | **下标槽** |
| 0x11/0x14 | SET_MEMBER3/4 | **对象槽** | **键槽**（bit31=1 → 常量名） | **值槽** |
| 0x13 | RAWSET | **对象槽** | **键槽** | **值槽** |
| 0x12 | CONCAT_MEMBER | **表槽** | **键槽** | **待追加值槽** |
| 0x17 | METHOD_PREP | 目标（并把 B 槽拷到 A+1） | **对象槽** | **键槽** |

官方样本交叉验证（`lib/ide/aifix.aardio`，`tools/aardio_ctx.py`）：

```
=== /0/51/4  pc=133 GET_MEMBER3  A=1  B=1    C=268!   → 对象=局部槽1，键=常量12
=== /0/51/4  pc=134 INDEX        A=1  B=1    C=287!   → 对象=局部槽1，键=常量31("radius")
=== /0/51/4  pc=129 SET_MEMBER3  A=2  B=282! C=3      → 对象=局部槽2，键=常量26，值=局部槽3
```

`0x17 METHOD_PREP` 在官方样本里的形态也一致：
`pc=18 METHOD_PREP A=3 B=3 C=256!`（`const[0] = "import"`）→ 把对象复制到 A+1，
再取 `B[C]`。

#### 7.5.4.4 0x32 BUILD_ARRAY 的两个操作数

官方 case 0x32（`decomp` 880-923）：

* `B`（bits 23..31）= **元素个数**：元素取自槽 `A+1 .. A+B`，
  按 `A+B, A+B-1, …, A+1` 的顺序追加进 A 槽那张表的数组部分；
* `C`（bits 14..22）= **容量提示**：`local_13c = C*0x32 - 0x32 + B`，
  即表需要的容量；`C == 0` 时提示值写在紧随其后的 u32 里（并吃掉一条记录）；
* `B == 0` 时元素个数改由**调用帧的返回槽**反推（`(retSlot - A)/16 - 1`），
  这条要等调用帧落地才能实现。

官方样本：

```
=== /0  pc=676 BUILD_ARRAY A=9 B=50 C=1     → 追加槽 10..59 共 50 个元素（容量 50）
=== /0  pc=708 BUILD_ARRAY A=9 B=31 C=2     → 再追加槽 10..40 共 31 个（容量 50+31=81）
```

第一条 `C=1`（原来 0 个）→ 容量 `1*50-50+50 = 50`；
第二条 `C=2`（原来 50 个）→ 容量 `2*50-50+31 = 81` ✓。

#### 7.5.4.5 本轮的落地

* 引擎规格表 `engine/aardio_chunk.cpp` 的 `kKindTable`：按上表改写 14 条角色说明；
* 记录 VM `engine/aardio_vm.cpp`：
  * 算术（0x18-0x1D）与位运算（0x35-0x3B）改成「左 = B、右 = C」；
  * 新增**成员访问族** 0x05/0x06/0x07/0x08/0x09/0x0A/0x0B/0x0C/0x0D/
    0x10/0x11/0x12/0x13/0x14/0x17 与 **0x32 BUILD_ARRAY**；
  * 官方表语义落地：整数键走数组部分（1 基）、字符串键走哈希部分、
    命中为 null 时回落到父表（表 +0x08，引擎侧是 `Table::parent`）；
* 可执行记录种类：**30/61 → 46/61**。

### 7.5.5 调用帧与闭包（第十六轮定案）

第十六轮把「调用族 + 闭包 + 上值」这三组记录的角色彻底定案，
Nodio 的记录 VM 据此落地 **52/61** 种记录。

#### 7.5.5.1 调用约定

| 项 | 结论 | 证据 |
| --- | --- | --- |
| 被调值 | 槽 `A` | `FUN_004D3040` 的 `in_EAX` = `&slot[A]`；`in_EAX[2]` 是该槽的类型标签 |
| 实参窗口 | 槽 `A+1` .. `A+B-1`（`B-1` 个值，第一个是 self） | 0x2B 原生分支把 `[&slot[A], &slot[A+B])` 整段复制；官方样本 `/0/1` 的 `CALL A=3 B=4` 恰有 3 个暂存值（槽 4/5/6） |
| 返回槽 | 槽 `A+B` | 0x2A 装参块 `0x004C5A44`：`B != 0` → `vm->0x08 = &slot[A+B]` |
| 官方传入的「实参个数」 | `C-1`（`C == 0` → `-1`，变参） | 同一块：`ESI = C; DEC ESI; PUSH ESI` → 帧 `+0x10` |
| 帧槽布局 | 槽 0 = self，槽 1.. = 显式参数；局部变量与参数共用一片槽 | 官方样本 `/0/0` 的 `LOAD_LOCAL B=1` = 第一个显式参数；`/0/1` 的 `LOAD_LOCAL B=2` = 第二个 |

> **`C` 的确切含义仍未定案**：官方样本里同一个 `C=2` 既出现在「1 个显式参数」
> 的调用上，也出现在「3 个显式参数」的调用上（`/0` 的 `CALL A=8 B=5 C=2`
> 暂存了 4 个值）。因此 Nodio **不**用 `C` 裁剪参数，只把它记进帧里当提示；
> 参数个数一律由 `B`（实参窗口长度）决定。

#### 7.5.5.2 闭包与上值

* **闭包对象**（官方 `FUN_004D50A0`，type 6）：
  `+0x07` = 上值个数、`+0x10` = 属主命名空间、`+0x14` = 闭包体（嵌套对象）、
  `+0x18` = 上值数组。
* **捕获条数 = 嵌套对象的 `flags[0]`**（运行时 chunk 帧 `+0x48`）。
  官方校验器 `FUN_004D4450` 的 `case 0x34` 与解释器 `case 0x34` 都取这个字节：
  ```c
  uVar9 = (uint)*(byte *)(*(int *)(*(int *)(param_1 + 0x10) + uVar9 * 4) + 0x48);
  ```
* **紧随其后的 N 条记录是捕获项**，且会被**消费**（ip 前进 N 条）：
  * kind `0x03`（LOAD_UPVALUE）→ 捕获**当前作用域**的上值数组第 `B` 项（共享 cell）；
  * 其他（官方用 kind `0x04` / LOAD_LOCAL）→ 为当前帧的局部槽 `B` 建「盒」
    （`FUN_004D5210`，type 10），**按引用**。
* **上值按引用**：`0x0E STORE_UPVALUE` 写的是定义帧的那个槽本身，
  所以闭包里的赋值对定义者可见。

#### 7.5.5.3 官方样本的全量自证

对官方唯一样本 `aifix.aardio` 的 **96 个 `0x34` 记录**逐个校验
「捕获条数 = 嵌套对象 `flags[0]` 且紧随的 N 条记录必须是 kind 3/4」：

```
NEW_CLOSURE total=96  violations=0
```

> 这条自证顺带纠正了第十五轮的一处误判：根对象的子对象是 `/0 /1 /2 /3`
> （**4 个**），此前把根的 `/1` 误记成了 `/0/1`，才产生「捕获条数与后继记录
> 矛盾」的假冲突。

#### 7.5.5.4 Nodio 的落地方式

* 记录 VM 改为**帧栈**（`std::vector<RtFrame>`），每帧独立槽数组
  （官方是就地压栈，语义等价但更安全）；
* 闭包值不塞进引擎的 `Value` 枚举：记录 VM 自己的 `RtSlot` 上加
  `std::shared_ptr<RtClosure>`（type 6），闭包以 `Value::Pointer` 存进表 /
  槽并由 VM 的保活区兜底；
* 上值用 `RtCell`（盒）建模：捕获局部时把该槽**装箱**，此后局部与上值
  共享同一份存储 → `STORE_UPVALUE` 的写入能透传；
* 新增合成夹具 `call` / `params` / `upvalue`（`tools/aardio_make_chunk.py`），
  分别验证「闭包调用 = 10」「self + 参数1 = 7」「上值按引用改写外层局部
  10 → 99」；再加一个**递归闭包**夹具（闭包先存进模块命名空间、再用
  `GET_MEMBER` 取回自己递归调用，`f(5) = 120`）；
  回归 `tests/aardio_run_check.ps1` 45 → **58 项**。

### 7.7 与编译侧描述符表的关系（第十三轮修正）

第十轮曾断言「描述符表在运行期不成立，解释器每个 kind 都只取 9 位操作数」。
**这个断言是错的**，第十三轮被官方校验器 `FUN_004D4450` 与运行期解释器
的对照读出推翻：

* 描述符表 `DAT_007C80A0` **确实决定每种记录的操作数格式**：
  bits 0..1 分「三操作数 / 单 18 位 / 单 18 位有符号」三档，
  bits 2..3 与 bits 4..5 分别是 C、B 两个操作数的**寻址类别**；
* 解释器里 **18 位操作数是真实存在的**：类别 1 的记录
  （`0x00/0x05/0x07/0x0C/0x0D/0x34`）取的是 `word >> 14`（**没有 9 位掩码**），
  用作**常量表下标 / 嵌套对象下标**；
* 描述符表 bit6（可作断点落点）、bit7（后必须紧跟 `0x22`）**在运行期没有读取点**——
  这部分只在**校验期**用；
* 「校验器与解释器对 kind `0x22` 解读不一致」这条疑问现在有了解释：
  校验器把 `0x22` 当**类别 2**（单 18 位有符号 = 位移），
  而第十轮读到的「跳过 B 条记录」其实是校验器在**扫跳转落点处的
  `BUILD_ARRAY` 配对**（`0x32` 记录必须成对），不是另一种语义。

结论（修正后）：**描述符表是编译期与校验期共用的「操作数格式表」**，
运行期按它决定取几个操作数、每个操作数几宽；§7.2 的位布局仍然成立，
但必须配合描述符表与寻址类别（§7.5.2）才能正确解码。

| 0x32 BUILD_ARRAY 的两个操作数 | ✅ **第十五轮已解**：`B`=元素个数（源槽 A+1..A+B），`C`=容量提示（`C==0` 时提示值在下一条 u32）；`B==0` 需调用帧（§7.5.4.4） |

| `CALL` 的 `C` 操作数的确切含义 | ⏳ **仍未定案**：官方传 `C-1` 作为「实参个数」，但样本里同一 `C=2` 对应过 1 个与 3 个显式参数；Nodio 改用 `B` 决定实参个数（§7.5.5.1） |
| 0x2F/0x30/0x31/0x3C 的调用变体 | ⏳ 第十六轮只落地 0x29/0x2A/0x2B；多返回值调用（0x2F）与命名空间调用（0x31）待补 |
| 记录流 → **AST** 的结构编码 | ✅ **第十三轮撤销该问题**：官方运行期没有 AST，解释器 `FUN_004C4BC0` 直接执行扁平记录流；因此**不需要**反推树，路线改为「照官方做记录 VM」（见 §7.5.2） |
